How a task goes from your words to a merged pull request, which steps run side by side, and why each one is done by the session, by a subagent or in the background.

Why in parallel: the searches and the download don't depend on each other, and each answers its own question. Why subagents: a wide sweep reads dozens of files the session never needs again; a subagent reads them and hands back only the answer, so the session's context stays free for the conversation with you. §2One task
Pick one task; give the others as ready-to-paste lines
Why the session: deciding what you asked for first is a judgement about your words, and it takes seconds.
§3Round 1
What I understood, proposed criteria, and questions only if neededEach criterion about the app is a Gherkin (its screens, its title, its rounds), and becomes one e2e scenario. A question only where a point has two readings that lead to different changes. None is fine.
You answer
Why the session: it's a conversation, and a subagent can't ask you anything. Why questions are optional: a question that changes nothing costs you a round for no gain.
§4Round 2: spec

You say go, and agree the split
Why the split is in the spec: you see and agree it before any tokens are spent on it, and the PR keeps a record of how the work was done.
§5Work
Branch claude/<slug>; when splitting, write the contract firstDomain types or a short doc each subagent builds against.
rule-author × NOne per build element. Each writes only its own rules/… files.
build-extractorA new or changed build note → build.yaml, note-map.md.
Other writing subagentOnly for a part the spec's "How the work splits" names.
Merge the worktrees, then everything shared, oncetools/manifest/, discrepancies.md, docs, CLAUDE.md. Then dotnet build Loopsmith.slnx + dotnet test.
Why in parallel: build elements are independent by design: each rule file describes one element, with its own provenance. Several rule-authors can run side by side. Why each prompt names its binding rules: a subagent starts without the conversation, so it only follows the rules it is told. Why worktrees and disjoint folders: two agents never write the same file, so the merge is mechanical. Why the contract first: without it, two writing subagents drift apart and the merge costs more than the split saved. Why the shared files wait: rules/manifest.yaml is generated from every rule, and discrepancies.md collects every agent's findings, so each is written once, after all of them.
§5Check
conventions-reviewerThe diff against docs/CODING_RULES.md.
Criteria checkEach acceptance criterion against the diff; each Gherkin is one scenario, word for word.
Browser checkOnly for a web change: publishes the app, checks it at desktop and 390 px and the console.
tools/e2e/record.sh --changed-since origin/main / dotnet testLong runs in the background meanwhile. Every scenario the branch adds or changes passes on each screen it is played on, and each GIF shows what its Gherkin says.
Fix what they found
Rebase onto origin/main, build + test again, then the first pushThe branch stays local until now. Only before the first push: after it, a rebase would need a force-push.
Why the rebase: a conflict with main shows up in the session, before the PR opens, and the build and test run against the current main. A PR that falls behind main later needs nothing: it doesn't have to be up to date to be merged. Why subagents: a fresh reader sees what the author overlooks, because it doesn't share the session's assumptions. Why in parallel: the checkers only read, so they can't get in each other's way. Why before the push: every push runs CI; a fix found now saves a round on the PR. Why the session records the e2e scenarios: CI doesn't run them, so the session's recording is their only run, and it is the proof the session checked its own work.
§5PR
Open the PR, rename the session, subscribeMessages end with the PR and preview links; a docs-only PR has no preview, so only the PR link.
tools/e2e/push-gifs.shOnly when scenarios were recorded: pushes their GIFs to a throwaway e2e-gifs/pr-<n>-<sha> branch; the "E2E videos" workflow posts them on the PR as ## Scenarios (V<N>) (each scenario's Gherkin, then its 🖥️ Desktop and/or 📱 Mobile GIF) and deletes the branch.
Why the session: one writer to GitHub, so nothing is posted twice and every reply comes from the session that knows the whole history. Why the GIFs travel on a branch: a session can't upload a file to GitHub, but it can push; the workflow only moves them into the prs-resources release and posts them, it builds and records nothing.

Your review, comment or message
A CI result, a conflict, a check-in about every 4 hOn a conflict: merge origin/main, build, test, push.
CI diagnoserOnly on a red check with a long log.
Fix, reply on the thread, pushNever resolve the thread: you resolve it. A push that changes e2e scenarios: record them before it, tools/e2e/push-gifs.sh after it.
Why a diagnoser: a long CI log would fill the session's context; a subagent reads it and names the cause. Why pushes stay sequential: each push runs CI and may post a new e2e version (V1, V2…), and the PR's history should read in order. Why you resolve threads: it's your sign-off before merging.
§6Follow-ups
Each one launched as its own session when you say so
Why separate sessions, not subagents: a follow-up needs its own spec agreed with you and its own PR. It's a different task, not a part of this one.

Why it's built this way

The session is the only writer

It alone talks to you, commits, pushes and posts on GitHub. Whatever a subagent does comes back to the session first, so there is one history, one voice on the PR and nothing is pushed twice.

Context is the scarce thing

The session carries your words, the spec and every round of review. Subagents do the reading-heavy work (wide searches, long logs, second looks) and return only conclusions, so that context stays sharp.

Parallel only where work is independent

Searches, checks and separate build elements don't depend on each other, so running them side by side saves time and risks nothing. The rounds with you, the pushes and the shared files depend on what came before, so they stay in order.

Split only what's worth splitting

Each subagent starts without the conversation and must be told the rules. That briefing costs time and tokens, so a one-file change stays in the session, and so does anything the spec didn't split.

A fresh reader catches more

The author of a change reads it with its own assumptions. A subagent that only knows the spec and the diff checks what is actually there.

The merged result is what counts

Each worktree may pass on its own, but only the merged branch ships. The session runs the full build and test suite on it before any push.
