The slices that exist today are listed in CONVENTIONS.md.

01Problem statement

Build guides (Mactics, Plunderthebooty) explain loops as trigger → effects → why. Players re-derive this by hand in notes. Existing tools show what is equipped, never what happens when you play it.

Gap 1 · No causality data

Bungie and Clarity describe items in prose. Nothing machine-readable says “this fires when that happens”.

Gap 2 · Scattered sources

Clarity has hashes but no abilities, artifact perks or cooldowns. The Compendium has them — as spreadsheet prose with no hashes.

Gap 3 · Non-linear math

Energy refunds scale with ability cost (chunk energy scalar); effect order changes damage results.

02Goals & requirements

Backend first, in C# / .NET 10. UI comes later and just renders what the API returns.

In scope (v1)

  • Compose builds like DIM: class, subclass, abilities, aspects, fragments, armor mods, artifact mods, exotics, weapons + perks
  • Step-by-step simulation: user picks the next action, engine returns effects + what's now available
  • Every effect explained: source element + reason text
  • Local copy of all game data, refreshed on patch

Out of scope (v1)

  • Frame-accurate real-time / DPS simulation
  • PvP, enemy AI, positioning
  • Bungie OAuth inventory import (later)
  • The UI itself

Functional

IDRequirement
FR-1Browse catalog by class, element and kind (aspect, fragment, mod, exotic, weapon perk…).
FR-2Create / save / share a build. Validate: aspect-granted fragment slots, armor energy, one exotic armor, one exotic weapon.
FR-3Simulate one action against a state: returns new state, ordered fired rules, available next actions.
FR-4Simulate a sequence (a whole loop) and return the full trace.
FR-5Resolve cascades: effects that are triggers fire further rules (bounded depth).
FR-6Each fired rule carries source element, trigger, effects and human-readable reason.
FR-7Coverage report: items with no authored rules, Compendium names that don't resolve to a hash, and rule numbers that disagree with the Compendium.
FR-8Builds pin a catalog version, so old builds still replay after a patch.
FR-9Ingest a dated Compendium snapshot (your script's per-tab output); every number keeps its provenance and certainty (known / approximate / unknown).
FR-10Generate draft rules from the Compendium's “On X:” phrasing for a human to confirm.

Non-functional

Deterministic

Same build + state + action ⇒ same output. Golden tests from real notes.

Fast

< 50 ms per step; catalog snapshot cached in memory.

Fresh

Auto-ingest when the Bungie manifest version changes.

Auditable

Rules live in git; every number traceable to a Compendium tab/row, a Clarity hash or a rule file.

Enforced

Architecture tests in CI guard slice boundaries and restricted constructors.

04Architecture — vertical slices

Group by feature, never by kind: a behaviour change touches one slice, not a layer. Feature slices depend only on the shared kernel; only Orchestration sees every slice. One project — slices are folders.

05Coding conventions (binding)

Requirements, not suggestions — they win over anything else in this proposal. They live in CONVENTIONS.md; the why goes in ADRs.md, which explains but never overrides.

Architecture

  • Vertical slices: group by feature, never by kind
  • Slices depend only on the kernel (Domain, Functional); Orchestration → all
  • Domain = data + pure value arithmetic only; no System.IO, no slice dependency
  • Architecture tests enforce every boundary in CI

Functional design

  • Strict impure → pure → impure sandwich: read first, compute, write last
  • A statement is pure or impure — never nested on one line
  • Effects as data: pure code returns an Effect DU, the shell executes it
  • Own Optional / Result / Unit (Dunet) — no third-party FP library, no null-as-absence, no exceptions as control flow
  • Railway for flows · typestate where order matters · pure state machine only for genuinely multi-state things (GameState)

Domain modelling

  • Data ⟂ behaviour: records hold data; logic lives in static / extension functions
  • Every function name has a verb (Is/Has/Can, Parse/ToX/FromX allowed)
  • Immutable records everywhere; DUs via Dunet, never inheritance
  • Illegal states unrepresentable: data-carrying cases, not tag + optionals
  • Value objects via Vogen, validated at the boundary
  • Named failure / Severity only where the app branches on it

API gotchas

  • Static direct calls over interfaces / delegates
  • Dunet has no static factories: new Result<T, F>.Ok(x), Optional.Some(x), Optional.None<T>()
  • Match<T>(…) needs the explicit type argument when branches return different types
  • Catch foreseeable exceptions at the boundary → Result; let unrecoverable ones bubble

The sandwich, in code

// Orchestration/IngestionShell.cs — read top to bottom: impure, pure, impure
public static async Task RunIngest(HttpClient http, LoopsmithDb db, string rulesDirectory, CancellationToken ct)
{
    var sources = await SourceFetching.FetchSources(http, rulesDirectory, ct);   // impure: read

    var effects = IngestionPlanning.PlanIngest(sources);                          // pure: ROP → Effect[]

    await EffectExecution.ExecuteEffects(db, effects, ct);                        // impure: write
}

// Orchestration/StepSimulation.cs
public static async Task<Result<Resolution, string>> SimulateStep(LoopsmithDb db, SimulateRequest request, CancellationToken ct)
{
    var catalog = await Persistence.LoadCatalogSnapshot(db, request.CatalogVersion, ct);   // impure
    var build   = await Persistence.LoadBuild(db, request.BuildId, ct);                    // impure

    var resolution = catalog                                                               // pure
        .Bind(c => build.Bind(b => BuildValidation.ValidateBuild(b, c)))
        .Map(validated => ActionResolution.ResolveAction(validated, request.State, request.Action));

    return resolution;
}

// Loopsmith.Api — the host only maps HTTP in and out
app.MapPost("/api/simulate", async (SimulateRequest request, LoopsmithDb db, CancellationToken ct) =>
{
    var resolution = await StepSimulation.SimulateStep(db, request, ct);          // impure
    var response   = resolution.Match<IResult>(                                   // pure
        ok    => TypedResults.Ok(ResolutionMapping.ToResponse(ok)),
        error => TypedResults.Problem(error, statusCode: 400));
    return response;
});

07Domain model

An aspect, fragment, mod, exotic perk and weapon trait all have the same shape: an element with rules. “Kill with Threaded Spike → Unraveling rounds” (fragment) and “Melee kill → Super energy” (mod) are structurally identical. Records hold data; behaviour is static functions in the slices.

Authoring a rule (YAML, keyed by manifest hash)

- hash: 0000000000          # resolved from the manifest by name
  name: Stylish Executioner
  kind: Aspect
  source: compendium/2026-10-09/Prismatic#54     # provenance, shown in the trace
  rules:
    - on:   { killDebuffed: { via: Any, targetHas: [AnyElementalDebuff] } }
      then:
        - { applyBuff: { status: Invisibility, duration: 8s, stacks: 1 } }
        - { applyBuff: { status: Truesight,    duration: 4s, stacks: 1 } }
      reason: "Killing a debuffed enemy grants Invisibility and Truesight."
    - on:   { damage: { via: Melee } }
      when: [ { has: Invisibility } ]
      then:
        - { modifyDamage: { against: Melee, multiplier: 4.0 } }   # 300% increased [PvP 20%]
        - { debuffTarget: { status: Weaken, duration: 5s } }
      reason: "Melee while invisible deals 300% more damage and weakens."

RuleParsing.ParseRuleFile turns this text into Result<RuleSet, string>; the YAML DTOs never leave that slice. It also checks every status against the Compendium glossary — Truesight isn't one of its 36 entries, so it is flagged for the vocabulary instead of silently accepted. RuleDrafting would have produced most of this entry from the Compendium text; you confirm the numbers and the trigger.

08Simulation engine

The app flow around it is a railway. GameState itself is the one genuinely multi-state thing (buffs, stacks, cooldowns, pickups), so it's a pure state machine: (state, event) → (state, fired), feeding new events back in, bounded.

// Simulation/ActionResolution.cs — pure: no I/O, no clock, no randomness
public static class ActionResolution
{
    public static Resolution ResolveAction(ValidatedBuild build, GameState state, PlayerAction action)

        var available  = ListAvailableActions(build, cascade.State);
        return new Resolution(cascade.State, cascade.Fired, available);
    }

Phase order inside a tick

1 · Debuff→ 2 · Empower→ 3 · Damage→ 4 · Spawn→ 5 · Refund→ 6 · Cascade

Order isn't commutative

Tractor Cannon's debuff must land before One-Two Punch's melee bonus is counted. Sort by ResolvePhase, never by equip order.

Energy isn't additive

Chunk scalars come from the Compendium: Lightning Grenade 0.5x, Threaded Spike 0.8x, Combination Blow 1x. So 3× Bomber's 20% is only 10% on Lightning Grenade — ScaleEnergyByCost.

Loops must terminate

Self-feeding chains (Combination Blow) need a depth cap and per-tick dedupe of (rule, event) pairs.

11Tech stack & solution layout

.NET 10 / C# 14

  • ASP.NET Core minimal APIs — host only: endpoints, DI, BackgroundService for manifest sync
  • Dunet for every DU; Vogen for every value object
  • Own Optional / Result / Unit in Functional/ — no third-party FP library
  • EF Core 10 + Npgsql, used only inside Persistence (Vogen-generated converters)
  • YamlDotNet / System.Text.Json / Markdig (Compendium tabs) only in the parsing slices; their exceptions wrapped once into Result<_, string>
  • xUnit + Verify (snapshot tests of traces)
  • ArchUnitNET or NetArchTest for the architecture tests
  • Built-in OpenAPI; optional .NET Aspire for local Postgres
